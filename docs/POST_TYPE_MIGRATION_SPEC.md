# Техническое задание: выделение Einsatzberichte в отдельный тип записей

Статус: код этапов A–D реализован, production-перенос не запускался. Дата: 27.09.2026.

## Текущее состояние реализации

- Добавлены регистрация CPT `einsatzbericht`, два формата URL и совместимое чтение `post` + `einsatzbericht` в основных выборках.
- Основная форма, быстрая форма и установочный пример создают CPT; основной редактор требует явную URL-категорию при нескольких выбранных Stichworte.
- Экспорт сохраняет исходный тип, импорт прежних архивов создаёт legacy-CPT, а новых сохраняет категорийную схему. Импорт останавливается при изменении slug или отсутствии URL-категории.
- Добавлены WP-CLI preflight, пакетный перенос, состояние и пакетный откат с журналом, блокировкой конкурирующих операций и проверкой контрольных сумм бэкапов. Перенос **никогда** не запускается при обновлении или активации.
- Локально проверены PHP lint, интеграционные тесты и HTTP-маршруты на изолированной WordPress 7.1; production-сайт и его данные не менялись.
- Перед production остаются обязательными staging-восстановление реальных бэкапов, HTTP-проверка каждого существующего URL и ручная приёмка по разделу 6. Порядок действий и команды: `docs/POST_TYPE_MIGRATION_RUNBOOK.md`.

## 1. Цель и неизменяемые условия

Перенести существующие отчёты о вызовах из стандартного типа WordPress `post` в отдельный тип `einsatzbericht`, не создавая копии записей и не меняя их публичные адреса. Новые отчёты создавать только как `einsatzbericht` с адресом `/einsaetze/{kategorie}/{postname}/`. Обычные записи блога остаются `post` и не смешиваются с отчётами в админке, блоге, RSS и стандартных выборках.

Инварианты:

1. Для каждого существующего **публичного** отчёта `get_permalink($id)` до и после миграции возвращает **побайтно одинаковый URL**, включая путь и завершающий `/`. Запрос старого URL возвращает `200`, без `301/302` и без смены `rel=canonical`. Для черновиков, приватных и отложенных отчётов сохраняются статус и действующие правила доступа/предпросмотра.
2. Для нового отчёта категории `FEUBMA` и slug `feubma-luruper-hauptstrasse-3` URL имеет вид `/einsaetze/feubma/feubma-luruper-hauptstrasse-3/`.
3. Публичная страница `/einsaetze/`, её вёрстка, карта, карточки, фильтры и пагинация визуально и функционально не меняются.
4. ID записи, slug, статус, даты, автор, заголовок, текст, excerpt, комментарии, ревизии, все существующие `_feu_einsatz_*` meta, категории, изображения, вложения, назначения участников, логи и статистика сохраняются.
5. До начала миграции подготовлена проверенная резервная копия базы данных и `wp-content/uploads`; миграция не запускается автоматически при обновлении или активации плагина.
6. Необратимого удаления данных и автоматического пересоздания картинок в ходе миграции нет.

Единственное намеренное изменение публичных выборок: вызовы перестают попадать в обычную ленту блога/RSS. Содержимое самого раздела вызовов и его оформление остаются прежними.

## 2. Текущее состояние и границы совместимости

- Сейчас отчёт создаётся как `post` и распознаётся по `_feu_einsatz_einsatzbericht=1` (`includes/class-admin.php`, `includes/class-schnelleingabe.php`).
- Текущий плагин строит публичный URL как `/einsaetze/{postname}/` через фильтр `post_link` и собственное rewrite-правило (`includes/class-public.php`). Поэтому существующие URL нельзя переводить на трёхсегментную схему.
- Ряд запросов статистики и реестра жёстко содержит `post_type = 'post'` (`includes/class-database.php`, `includes/class-template-helpers.php`). Импорт архива также создаёт `post` (`includes/class-backup-manager.php`). Замена только формы создания записей недопустима.
- Корневая категория `Einsätze` и её дочерние категории остаются существующей таксономией WordPress `category`. ID терминов и значения опций `feu_einsatz_categories` сохраняются. Отдельная таксономия не входит в эту миграцию.
- Таблицы содержимого WordPress остаются прежними (`wp_posts`, `wp_postmeta`, `wp_term_relationships`; фактический префикс сайта может отличаться от `wp_`). Новый `post_type` — логическое разделение, не новая таблица с постами.

## 3. Контракт нового типа и URL

### 3.1. Регистрация типа

- Ключ типа: `einsatzbericht`; UI-название: `Einsatzberichte`.
- Регистрация на `init`, `public=true`, `publicly_queryable=true`, `show_ui=true`, `show_in_menu=false` (пункт списка остаётся внутри существующего меню плагина), `hierarchical=false`, `has_archive=false` (путь `/einsaetze/` уже занят страницей обзора).
- Поддержка необходимых полей WordPress: title, editor, author, excerpt, thumbnail, comments, revisions. REST-доступ включать только если он действительно нужен редактору; при включении применять те же права и ограничения к meta.
- Зарегистрировать `category` для CPT. Текущая реализация использует существующие базовые WordPress capabilities и дополнительный серверный `map_meta_cap`-ограничитель по матрице ролей плагина; создание напрямую через штатный CPT UI запрещено. REST отключён. Отдельные primitive capabilities остаются возможным последующим усилением, не условием автоматического переноса.
- Не полагаться на стандартный `rewrite.slug` для обоих форматов сразу. Для CPT использовать `post_type_link` и явные, узкие rewrite-правила. Перестроить rewrite-правила **один раз** при установке поддерживающей версии, не на каждом запросе.

### 3.2. Старые отчёты

- Перед изменением типа снять снимок текущего `get_permalink()`, `post_name`, категорий, статуса и даты. Старый канонический путь зафиксировать в защищённом meta-поле `_feu_einsatz_legacy_path` (только относительный путь внутри сайта) и установить `_feu_einsatz_url_scheme=legacy`.
- После изменения `post_type` фильтр `post_type_link` возвращает именно сохранённый старый путь. `post_name` не менять. Старый rewrite `/einsaetze/{postname}/` ищет только `einsatzbericht` с признаком `legacy`; он не должен перехватывать обычные страницы/записи или раскрывать черновики.
- Изменение заголовка или категорий не меняет URL старого отчёта. Смена URL допускается только отдельной явной операцией с предварительным просмотром и созданием адресного redirect; в рамках этой миграции такой операции нет.

### 3.3. Новые отчёты

- При создании задавать `_feu_einsatz_url_scheme=category`, ID основной категории `_feu_einsatz_primary_category_id` и зафиксированный slug `_feu_einsatz_permalink_category_slug`.
- Основная категория должна быть существующим дочерним термином корневой `Einsätze`. Если выбранных категорий несколько, основную выбирает редактор явно; без неё публикация запрещена. Slug категории должен быть однозначным внутри дерева `Einsätze`.
- URL собирается строго как `/einsaetze/{category-slug}/{post_name}/`. Категория или её slug не меняют опубликованный URL задним числом; расхождение показывается редактору как предупреждение.
- Rewrite для трёх сегментов проверяет существование CPT-записи, её публичный статус и совпадение категории URL с сохранённым slug. Несоответствующий путь — `404`, а не произвольный подбор «похожего» отчёта.
- Дубли `post_name`/полного пути обнаруживаются до публикации. Черновики и приватные отчёты не получают общедоступный маршрут; предварительный просмотр работает только через штатную авторизацию WordPress.

## 4. Порядок разработки и миграции

### Этап A — совместимая версия кода без переноса данных

1. Ввести единую функцию определения отчёта и набор допустимых типов: старый `post` с явной меткой и новый `einsatzbericht`. Не включать в миграцию обычный `post` только по адресу, названию или категории.
2. Обновить создание отчёта, редактирование, быструю запись, установочные примеры, очередь карт, сохранение meta, комментарии, авторизацию, ссылки списка и действия Dashboard для CPT.
3. Обновить все `WP_Query` и SQL с жёстким `post_type='post'`: обзор, связанные вызовы, архивы, статистику, графики, реестр улиц, поиск, участники, удаление данных и очередь карт. На переходе читать оба типа, всегда дополнительно проверяя `_feu_einsatz_einsatzbericht=1`.
4. Обновить одиночный шаблон, SEO/canonical, Open Graph, карты, шаринг, sitemap, RSS и `get_edit_post_link` для нового типа. Старые записи пока не переносить.
5. Импорт/экспорт: добавить в манифест схему URL (`legacy`/`category`) и основную категорию. Старые архивы без этих полей импортировать как legacy-CPT; не оставлять `post_type='post'` по умолчанию. При конфликте URL импорт останавливается с явной ошибкой, а не добавляет молча суффикс `-2`.
6. Запустить тесты двух типов и обоих форматов URL до появления кнопки миграции.

### Этап B — preflight и резервная копия

1. Только явно запрошенный запуск администратором или защищённая WP-CLI команда. Сначала обязательный dry-run без записей в БД.
2. Составить фиксированный перечень ID: `post_type=post` и `_feu_einsatz_einsatzbericht=1`, включая publish, future, private, pending, draft и trash; ревизии и вложения не преобразовывать.
3. Отдельно показать потенциальные «неразмеченные» вызовы (по метаданным или категории), но **не мигрировать их автоматически**.
4. Для каждого ID проверить текущий URL, конфликт маршрута, уникальность slug, наличие категории, владельца, статуса, файлов карты и связей с участниками. Неожиданный URL/конфликт — остановка и ручное решение.
5. Создать полную резервную копию БД и uploads. Проверить её восстановлением на staging и контрольными суммами. Резервная копия должна лежать вне публичного web-root либо в хранилище с запретом HTTP-доступа и ограниченным сроком хранения.
6. Зафиксировать исходные количества по статусам и контрольные суммы ключевых полей/meta/терминов, а также выборку публичных URL и ответов HTTP.

### Этап C — перенос

1. На время переноса запретить **только запись отчётов** через редактор, REST, AJAX и CLI; публичное чтение сайта не останавливать. Новые отчёты после снятия блокировки создаются как CPT.
2. Мигрировать ограниченными пакетами (например, 50–100 ID), по зафиксированному списку. Перед каждой записью повторно проверять `post_type=post`, метку отчёта и неизменность исходного состояния. Не использовать `OFFSET` по изменяемой выборке.
3. Для изменения одного поля типа применять штатный `set_post_type($id, 'einsatzbericht')`; не создавать новый пост и не переписывать title/content/date/guid. До изменения типа записать защищённый маркер и URL, после — проверить результат. Карты/внешнюю геокодировку и публикационные уведомления не запускать.
4. Вести устойчивый журнал по `run_id` и ID: исходный тип и URL, этап, результат проверки, код ошибки и время. Не записывать содержимое отчётов, координаты или персональные данные участников. Повторный запуск продолжает незавершённое и не дублирует уже проверенное.
5. После пакета: сверка количества, исходного и нового URL, статуса, meta, категорий, комментариев, файлов карт и назначений участников. Ошибка — остановка следующего пакета, а не продолжение «best effort».
6. После полного переноса пересчитать счётчики категорий, очистить только относящиеся к плагину кэши статистики/обзора/карт и обновить sitemap. Не выполнять глобальную очистку всех медиа или настроек.

### Этап D — приёмка и откат

- На staging и затем на production проверить URL каждого опубликованного legacy-отчёта сравнением `before/after`; результат `200` без redirect, тот же canonical. Для новых отчётов проверить трёхсегментный маршрут, `404` на ошибочную категорию и отсутствие доступа к черновикам.
- Сверить количества по статусам, статистику по годам, календарь, карту/изображение, участников, организации, архивы, комментарии, SEO-мета, поиск, RSS, sitemap, шаблоны и страницу `/einsaetze/`. Проверить права администратора, редактора и неавторизованного посетителя.
- При сбое мигрированные ID возвращаются в `post` по журналу, legacy-URL и meta сверяются с исходным снимком. Новые CPT-отчёты, созданные после миграции, **не удалять** и не конвертировать автоматически: совместимый код CPT должен оставаться активным до отдельного плана отката этих новых записей.
- Нельзя откатить только ZIP на версию без регистрации CPT после появления новых CPT-отчётов: это даст `404`. Документировать минимальную совместимую версию плагина и последовательность rollback.

## 5. Требования безопасности

1. **Права:** миграция доступна только администратору с `manage_options` и отдельной разрешённой функцией плагина. Каждое действие проверяет права на сервере; видимость кнопки не считается защитой. Новые CPT capabilities не должны открывать обход ограничений через `post.php`, REST или AJAX.
2. **CSRF:** действия админки выполняются только через POST с nonce, привязанным к операции и run ID; дополнительно проверяются права. GET-запрос, открытие страницы, обновление плагина и cron никогда не начинают перенос. Nonce сам по себе не заменяет проверку прав.
3. **Точный охват:** сервер сам выбирает ID по типу и явной meta-метке. Нельзя передать произвольный список ID или SQL через запрос. Все запросы с параметрами строятся через `$wpdb->prepare()`/API WordPress.
4. **Конкурентность и повтор:** один активный run на сайт, атомарная блокировка с токеном и временем жизни; безопасное возобновление после прерывания. Двойной клик, повторная отправка и параллельные процессы не меняют запись дважды.
5. **URL и доступ:** принимать только внутренние нормализованные пути, не использовать пользовательский URL как цель redirect. Meta-поля схемы и закреплённого URL нельзя изменять через обычную форму, REST или массовое редактирование; их изменяет только сервис миграции/отдельное привилегированное действие. Маршруты строго ограничены сегментами `einsaetze`, category и post slug; статус и права проверяются до выдачи содержимого или подсказки о существовании приватного поста. Все выводимые значения экранируются.
6. **Бэкап и приватность:** резервные копии и журналы недоступны через HTTP, не содержат паролей/nonce в логах, имеют ограниченные права доступа и срок хранения. В журнале фиксировать администратора, время, run ID, количество и ошибки, но не персональные данные участников.
7. **Отказоустойчивость:** на любой ошибке — остановка, понятное сообщение и сохранение журнала. Никакого `wp_delete_post`, изменения term ID или перезаписи медиа при переносе. Восстановление выполняется только после проверки целостности бэкапа.

## 6. Критерии готовности

- 100% старых публичных URL совпадают до и после миграции и возвращают `200` без redirect; старые непубличные записи остаются непубличными.
- 100% новых опубликованных отчётов имеют формат `/einsaetze/{kategorie}/{postname}/`; обычные статьи блога не попадают в список вызовов и наоборот.
- Сверка ID, количества по статусам, категорий, meta, вложений и назначений участников не показывает потерь; статистика до/после совпадает.
- Повторный запуск миграции ничего не меняет. Прерванный запуск успешно возобновляется. Проверен откат на staging.
- Пройдены PHP lint на поддерживаемых версиях PHP, WordPress integration-тесты, тесты rewrite/прав/архива и ручной браузерный smoke-тест редактора, карты, списка и пяти случайных старых/новых отчётов.
- Production-миграция запускается только после подписанного dry-run-отчёта, проверенного бэкапа и успешной приёмки на staging.
