# Перенос старых Einsatzberichte в отдельный тип записей

Этот порядок применяется только после установки совместимой версии плагина. Обновление плагина само по себе ничего не переносит. Старые отмеченные записи `post` продолжают работать до явного запуска миграции.

## 1. Подготовка

1. Установить совместимый код на staging, восстановить **реальную** копию базы данных и `wp-content/uploads`. Проверить права, карту, карточки, комментарии, архивы, участников, статистику и старые URL. Не использовать тестовые пустые файлы как бэкап.
2. Выгрузить полные бэкапы БД и uploads в закрытую директорию **вне** web-root. Убедиться, что они читаются только администратором сервера, восстановить их на staging и вычислить SHA-256 каждого файла.
3. На production использовать короткое окно обслуживания редакторов: публичное чтение доступно, запись отчётов блокируется на время run. Для варианта с WP-CLI временно добавить в `wp-config.php` `define('FEU_EINSATZ_ALLOW_POST_MIGRATION', true);`.
4. Пока перенос требует действий, администратор может открыть **Einsatzberichte → Datenmigration** и управлять переносом через формы. После проверки и завершения обеих миграций пункт исчезает из меню и уведомление больше не показывается. Для больших сайтов доступен также WP-CLI с `--user=<ID администратора>`. Браузерные действия защищены правом `manage_options`, nonce и явным подтверждением; флаг в `wp-config.php` нужен только WP-CLI.

## 2. Dry-run

```text
wp feu-einsatz migration-preflight --user=<admin-id> > preflight.json
wp feu-einsatz migration-status --user=<admin-id>
```

Проверить `errors` (должно быть пусто), `eligible_count`, список `records`, подозрительные неразмеченные записи в `warnings`, отсутствующие файлы карты, авторов и категории. Неразмеченные записи не переносятся автоматически. Записать исходные HTTP-статусы, canonical и точные URL всех опубликованных отчётов; устранить конфликты до запуска.

## 3. Запуск и контроль пакетов

В интерфейсе **Datenmigration** после успешной Vorprüfung указать абсолютные пути двух закрытых файлов и SHA-256, подтвердить восстановление на staging и ввести `START`. Нажать **Berichtsumzug starten**, затем **Nächste 10 Berichte übertragen** до завершения. При ошибке отдельного отчёта устранить причину и нажать **Erneut versuchen** в его строке. При прерванной Rücksetzung нажимать **Rücksetzung fortsetzen**; для начала Rücksetzung требуется ввести `ROLLBACK`. После запуска сохраняется журнал, поэтому повторное открытие страницы показывает текущее действие. Если Vorprüfung сообщает конфликт, кнопка запуска скрыта, а рядом с ошибочным отчётом есть **Bericht prüfen**. Не загружать файлы бэкапа через WordPress: форма проверяет уже существующие закрытые файлы на сервере.

Эквивалентные команды WP-CLI:

```text
wp feu-einsatz migration-start --user=<admin-id> --database-backup=<private-db-file> --uploads-backup=<private-uploads-file> --database-sha256=<64-hex> --uploads-sha256=<64-hex> --staging-verified=1 --confirm=START
wp feu-einsatz migration-status --user=<admin-id>
wp feu-einsatz migration-batch --user=<admin-id> --run=<run-id> --size=50
```

Повторять последнюю команду, пока `status=complete` или `status=partial_error`. Ошибка отдельного отчёта записывается в `failures`, а независимые отчёты продолжают перенос. При `partial_error` изучить `failures` и фактический тип записи; после устранения причины повторить только соответствующий ID:

```text
wp feu-einsatz migration-retry --user=<admin-id> --run=<run-id> --id=<failed-report-id>
```

Повторять для каждого проблемного ID до `status=complete`. Второй сбой одного отчёта автоматически создаёт очищенное диагностическое письмо для `dev@wdmin.com`; сообщение `wp_mail` означает приём почтовой системой, а не доставку. При `status=failed` старого журнала продолжить `migration-batch` с тем же `run-id`. Журнал вручную не менять. При неизменённой записи восстановление идемпотентно, включая прерывание между `set_post_type` и записью журнала. Изменённую редактором запись миграция намеренно не перезаписывает.

## 4. Приёмка

- Сравнить точные `get_permalink()` и HTTP `200` без 301/302 и canonical для **каждого** опубликованного старого отчёта. Проверить новую схему `/einsaetze/{category}/{slug}/`, неверная категория должна возвращать `404`.
- Сверить число ID и статусы, категории, meta, изображения, комментарии, назначение участников, карты, статистику по годам, архивы, sitemap, список `/einsaetze/` и обычную ленту блога.
- Проверить права администратора, редактора и гостя; черновики и приватные отчёты не должны становиться публичными.
- После успешной приёмки убрать временный флаг из `wp-config.php`. Хранить бэкапы по принятой политике срока хранения и доступа.

## 5. Откат

Если перенос не прошёл приёмку и записи после него не редактировали, использовать тот же совместимый код:

```text
wp feu-einsatz migration-rollback --user=<admin-id> --run=<run-id> --size=50 --confirm=ROLLBACK
wp feu-einsatz migration-status --user=<admin-id>
```

Повторять до `status=rolled_back`, затем снова сверить URL и данные. Откат работает в обратном порядке и не удаляет новые CPT-записи. Если после завершения переноса отчёты уже меняли, автоматический откат может остановиться на проверке отпечатка: сохранять журнал и восстанавливать из проверенного бэкапа по отдельному плану. **Не откатывать только ZIP плагина** на версию без CPT: новые записи перестанут открываться.
